# Phase 07.1: Close gap DS-03 — JDBC snapshot routing on execute path - Context

**Gathered:** 2026-07-24
**Status:** Ready for planning

<domain>
## Phase Boundary

Close the **DS-03 JDBC execute-path gap**: when `WorkflowRunContext.instanceId()` is set, V2 JDBC source/sink resolution must use run-start snapshot routing keys (`snap:{instanceId}:{name}`) so in-flight runs keep pre-reload pools; hot-reload must not redirect live JDBC traffic for active runs.

**In scope:** Fix `DefaultRuntimeJdbcEndpointResolver` managed-path return of `connectionName()` (with register-if-absent); ensure V2 QuerySource / PostGIS source factories and `JdbcRowSinkAdapter` push the resolved id; service-level Spring IT asserting `snap:` routing keys for source+sink under mid-flight reload; document execute-path authority vs catalog-side resolver.

**Out of scope:** Inline `dataSource` blocks (deferred); merging/deleting `JdbcCatalogResolver`; changing Kafka/ES snapshot paths (already wired); V1 writers; VO copy/restore around mutate; observable dual-DB behavioral proof (optional later); Playwright/UAT beyond the Java IT bar for this gap.

</domain>

<decisions>
## Implementation Decisions

### Fix locus
- **D-01:** Snap keys enter the execute path via the **resolver only** (`DefaultRuntimeJdbcEndpointResolver`) — not by scattering snap-key construction across adapters.
- **D-02:** Managed path: call **`catalog.resolve` then return `connectionName()`** (and register the pool under that key if absent) — mirror `JdbcCatalogResolver` semantics inside DefaultRuntime without depending on that class.
- **D-03:** This phase covers **managed `dataSourceId` only**; **inline `dataSource` blocks are deferred**.
- **D-04:** When snapshot/resolve fails under `WorkflowRunContext`, **fail fast** — **no fallback** to the logical catalog name.

### Source + sink coverage
- **D-05:** Cover **JDBC source and sink**; adapters/factories must push the **resolved** id (not the logical name).
- **D-06:** Source wiring continues to rely on existing **`QuerySourceFactory` `setDataSourceId` mutation** pattern.
- **D-07:** Required surface: **V2 `QuerySourceFactory` + `PostGisQuerySourceFactory` + `JdbcRowSinkAdapter`**; **no V1 writers**.
- **D-08:** **Accept existing VO mutate** side effects; **no copy/restore** in this phase.

### Proof bar for mid-flight isolation
- **D-09:** Minimum proof: **execute-path IT** exercising resolver + JDBC under mid-flight reload.
- **D-10:** IT must assert **both source and sink** resolution.
- **D-11:** Prove isolation via **pool/routing key assertion** — resolved id is `snap:{instanceId}:{name}` (and remains so after catalog reload). Dual DB-A/DB-B observable divergence is **not** required for this phase.
- **D-12:** IT lives as a **`@SpringBootTest` in `data-generator-service`** (catalog + hot-reload + resolver wired).

### Duplicate JDBC resolvers
- **D-13:** **Keep both** `JdbcCatalogResolver` and `DefaultRuntimeJdbcEndpointResolver` with clear ownership — **do not merge** in this phase.
- **D-14:** Fix snap return **inside `DefaultRuntimeJdbcEndpointResolver`** (align with catalog resolver semantics); **do not inject/delegate to `JdbcCatalogResolver`**.
- **D-15:** **`JdbcCatalogResolver` gets zero code changes** this phase (it already returns `connectionName()`).
- **D-16:** Document explicitly: **V2 execute path authority is `DefaultRuntimeJdbcEndpointResolver`**; `JdbcCatalogResolver` remains datasource-module / catalog-side resolution. Consolidation is a future concern.

### Claude's Discretion
- Exact IT class name, package, and whether to extend an existing Phase 7 hot-reload IT vs new focused class.
- How mid-flight reload is triggered in the test (catalog save API vs direct reload hook) as long as D-09–D-12 hold.
- Javadoc wording for D-16 as long as ownership is unambiguous for planner/executor.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `JdbcCatalogResolver.resolveManagedDataSourceId` — canonical pattern: `catalog.resolve` → `JdbcResolvedConnection` → `registerIfAbsent(connectionName)` → return `connectionName()`; **copy semantics into DefaultRuntime**, do not call this class.
- `DefaultRuntimeJdbcEndpointResolver` — already calls `catalog.resolve` for managed ids but **returns the logical `dataSourceId`** (gap to close).
- Phase 7 hot-reload / catalog tests in `data-generator-service` — extend or sibling for mid-flight snap-key IT.

### Established Patterns
- Managed JDBC resolve via `ConnectionCatalog` + dynamic routing pool registration.
- V2 source factories mutate VO `dataSourceId` after resolver returns.
- Fail-fast `IllegalArgumentException` / actionable errors on unknown catalog entries.

### Integration Points
- Spring bean wiring of `RuntimeJdbcEndpointResolver` → `DefaultRuntimeJdbcEndpointResolver` in service config.
- `WorkflowRunContext.instanceId()` must be present for snap pools to be selected by catalog resolve.
- Kafka/ES snapshot paths already correct — do not regress.

</code_context>
