<objective>
**Purpose:** Make transform/UDF failures actionable in run reports AND console job detail (XFORM-05). Per D-08 failure entries are rich: operator `type`/name + the failing transform step path (e.g. `transformers[2]`) + root-cause message, plus row/field locators when resolvable. Per D-09 errors surface in BOTH the run report and the console job detail reusing ONE structured shape (extend `RunReportCollector`). Per D-10 the policy is fail-fast — the first transform/UDF error terminates the run and reports the failing step + cause (per-row tolerance is out of scope).

**Output:** A new `TransformErrorVO` record (core model); an additive `transformErrors` component on `RunReportVO` with a null-normalizing compact constructor for back-compat (D-13); a `RunReportCollector.collectFailure(...)` that turns the runtime's located `IllegalStateException` into a `TransformErrorVO` (deriving the step path by matching the failing operator type to the template's transformer list); a `TaskExecutionService.markFailed(id, message, reportJson)` overload that persists the structured report on the failed row; failure-path wiring in `TaskController.runV2Tracked` and `DistributedJobLeaseRunner`; and embedded tests. The error reaches console job detail through the EXISTING carrier (no new field, D-09): `TaskExecutionService.toSummary` calls `parseReport(row.getReportJson())` to populate `TaskExecutionSummary.report` (a `RunReportVO`), which now carries the additive `transformErrors` from Task 1; `JobExecutionDetail.execution` IS that `TaskExecutionSummary`, so `JobExecutionDetail.execution().report().transformErrors()` exposes the structured error to the job-detail API response. The single shape is reused — no second error field is introduced (D-09).
</objective>

## Trust Boundaries
| Boundary | Description |
|---|---|
| TB-04-04-A | Runtime exception text (may contain row data) → persisted run report → console job detail |
| TB-04-04-B | Persisted historical report JSON → deserialization into the extended RunReportVO |

## STRIDE Threat Register
| Threat ID | Category | Component | Disposition | Mitigation Plan |
|---|---|---|---|---|
| T-04-04-01 | Information Disclosure | Error messages leaking raw PII / secrets into reports & job detail | mitigate | `TransformErrorVO.message` carries only the operator's already-sanitized cause (mask/json factories never echo raw values — 04-02); `collectFailure` copies the cause message verbatim without re-introducing row payloads; test asserts no raw value present. |
| T-04-04-02 | Tampering | Malformed/legacy persisted report JSON | mitigate | Additive `transformErrors` with null-normalizing compact ctor (D-13); legacy reports deserialize to an empty list (asserted), no breaking schema change. |
| T-04-04-03 | Denial of Service | Unbounded error text in report column | mitigate | Single fail-fast entry (D-10), not per-row accumulation; message is a single root-cause string; factories truncate value snippets (04-02). |
| T-04-04-04 | Repudiation | Failure not attributable to a step | mitigate | Step path derived from the template transformer list (`transformName(transformer,index)`) so every failure names its operator + index; fallback `step="transform"` guarantees an entry is always emitted. |
</threat_model>
