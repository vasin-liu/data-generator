# Phase 07.1 Plan 01: Fix DefaultRuntime managed snap return + ownership Javadoc Summary

**Managed JDBC execute-path resolve now returns `connectionName()` (the `snap:{instanceId}:{name}` routing key under an active run) instead of the logical `dataSourceId`, with register-if-absent implemented independently inside `DefaultRuntimeJdbcEndpointResolver`.**

## Performance

- **Duration:** ~64 min (dominated by two full reactor compiles that rebuilt the console-web frontend bundle via `frontend-maven-plugin`)
- **Started:** 2026-07-24T03:04:00Z
- **Completed:** 2026-07-24T04:08:00Z
- **Tasks:** 2
- **Files modified:** 1

## Accomplishments
- Managed JDBC source/sink resolve (`resolveSourceDataSourceId`, `resolveSinkDataSourceId`) now calls a new private `resolveManagedDataSourceId` that mirrors `JdbcCatalogResolver`'s `catalog.resolve` → validate `JdbcResolvedConnection` → `registerIfAbsent` → `return connectionName()` flow, closing the DS-03 execute-path gap where the resolver previously discarded the catalog result and returned the logical name.
- Fail-fast error handling: `IllegalStateException` when `ConnectionCatalog` is unavailable, `IllegalArgumentException` (via `CatalogResolveSupport.unknownConnection`) when the catalog entry is missing or not JDBC — no silent fallback to the logical `dataSourceId`.
- Expanded class-level Javadoc to explicitly name `DefaultRuntimeJdbcEndpointResolver` as the V2 execute-path JDBC authority while `JdbcCatalogResolver` remains the datasource-module catalog-side resolver — both coexist by design, consolidation deferred.
- `JdbcCatalogResolver.java` untouched (verified via `git diff --stat`); zero new dependency from `DefaultRuntimeJdbcEndpointResolver` to that class.
