<objective>
Add publish-time Template V2 validation that rejects references to unknown, unpublished, or deprecated UDFs, reusing the Phase 2 typed reference contract (D-27) and structured error codes — extending the existing `TemplateV2Validator` path and wiring it into the template publish gate only.

Purpose: UDF-06 requires that publishing a template referencing an unknown/unpublished UDF fails with a clear validation error, while draft saves stay lenient (D-09/D-11). This is the binding between templates and the UDF registry.
Output: a `UdfReferenceValidator` component, a reference-extraction helper in `TemplateV2Validator`, and a publish-gate call in `TemplateLifecycleService.publish`.
</objective>

    Add a static helper `collectUdfReferences(TemplateV2VO normalized)` to `TemplateV2Validator` that walks the template's transforms (same traversal the existing `validateTransform` uses) and returns a list of detected references per D-10/D-27: for each `SqlTransformVO`, scan `getSql()` for function-call tokens (compile a `Pattern` in the existing in-file style — an identifier-followed-by-`(` matcher, case-insensitive, mirroring the `SQL_JOIN`/`SQL_SELECT_DISTINCT` precedent), then **filter out tokens that appear in a curated built-in allow-list** (a `static final Set<String>` of standard SQL / Calcite built-in function names — e.g. `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`, `COALESCE`, `CAST`, `SUBSTRING`, `TRIM`, `UPPER`, `LOWER`, `CONCAT`, `NOW`, etc.; compare case-insensitively). **Every remaining non-built-in function token IS treated as a candidate SQL UDF reference (a `sqlName`) and MUST be validated** — this is what makes a truly-unknown, never-registered token detectable so it can raise `UDF_NOT_FOUND` (UDF-06 core case). Java/PF4J capabilities are NOT reference-validated (D-10) — exclude them. The built-in allow-list is the chosen false-positive control (planner discretion under D-12): built-ins are skipped, but any non-built-in function token is validated rather than silently ignored, so unknown `sqlName`s are NOT swallowed.

Collect all violations and throw a single structured exception listing them (aligned with `TemplateV2Validator` collection style, D-09). Write `UdfReferenceValidatorTests` using a real `UdfRegistryService` over `InMemoryUdfRegistry` (or a mock) covering: known published script udfRef passes; unknown id → UDF_NOT_FOUND; draft id → UDF_NOT_PUBLISHED; deprecated id → UDF_DEPRECATED; published sqlName in SQL text passes; a never-registered non-built-in SQL function token (the UDF-06 core case — not in the registry and not in the built-in allow-list) → UDF_NOT_FOUND; and a built-in SQL function token (e.g. `COUNT(...)`) is NOT flagged (allow-list skips it, no exception).

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Template YAML (operator-authored) → publish gate | Template content with UDF references crosses into the publish validation; references point at registry entries of varying lifecycle state |
| `UdfReferenceValidator` → `UdfRegistryService` | Reference resolution reads registry state to decide publish acceptance |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-04-01 | Tampering | publishing templates with dangling/unpublished UDF refs | mitigate | Publish-only hard fail: `UdfReferenceValidator.validate` rejects unknown (`UDF_NOT_FOUND`), draft (`UDF_NOT_PUBLISHED`), and deprecated (`UDF_DEPRECATED`) references before the template is marked PUBLISHED (D-11/D-12) |
| T-03-04-02 | Repudiation | unclear publish-failure cause | mitigate | Structured error codes + offending `field`/path are surfaced through `ConsoleApiAdvice` (03-02) so the operator sees exactly which reference failed (D-12) |
| T-03-04-03 | Denial of service | regex scan of SQL text | mitigate | Reference extraction uses bounded, anchored patterns in the existing `TemplateV2Validator` style over already-normalized template SQL (no catastrophic backtracking constructs); a built-in SQL function allow-list filters common built-ins so only non-built-in function tokens are resolved against the registry, bounding lookups |
| T-03-04-04 | Tampering | bypass via draft-save path | accept | Draft saves intentionally tolerate dangling references (D-11); the guarantee is enforced at the single publish gate, consistent with the template lifecycle FSM |
| T-03-04-SC | Tampering | maven/npm dependency installs | accept | No new package-manager dependencies are added in this plan; slopcheck N/A |
</threat_model>
